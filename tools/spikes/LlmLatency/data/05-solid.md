# Лекція 5. Принципи SOLID

[стор. 17]

## 5.1. Навіщо потрібні принципи проєктування

Програма, яка працює сьогодні, завтра зміниться: з'являться нові вимоги, нові формати, нові провайдери. Якість дизайну вимірюється тим, скільки коду доводиться змінювати для кожної нової вимоги і наскільки ризиковані ці зміни. П'ять принципів, відомих під абревіатурою SOLID, сформулював Роберт Мартін; вони допомагають будувати код, який легко розширювати й тестувати.

- **S** — Single Responsibility Principle, принцип єдиної відповідальності;
- **O** — Open/Closed Principle, принцип відкритості/закритості;
- **L** — Liskov Substitution Principle, принцип підстановки Лісков;
- **I** — Interface Segregation Principle, принцип розділення інтерфейсів;
- **D** — Dependency Inversion Principle, принцип інверсії залежностей.

## 5.2. Принцип єдиної відповідальності

Клас повинен мати лише одну причину для зміни. «Відповідальність» тут означає не одну функцію, а одне джерело вимог. Клас, який одночасно читає PDF, рахує токени, будує промпт і пише результат у базу даних, змінюватиметься з чотирьох різних причин: новий формат файлу, нова модель, новий текст промпту, нова схема БД. Кожна така зміна ризикує зламати інші частини класу.

Розділення відповідальностей зазвичай дає кілька невеликих класів: `PdfTextExtractor` витягує текст, `PromptFactory` будує запити, `LectureStore` зберігає дані. Кожен із них простіше зрозуміти, протестувати й замінити.

## 5.3. Принцип відкритості/закритості

Програмні сутності мають бути відкритими для розширення, але закритими для змін. Додавання нової поведінки не повинно вимагати редагування вже перевіреного коду. Типовий приклад порушення — довгий `switch` за типом, який доводиться доповнювати щоразу, коли з'являється новий варіант:

```csharp
// Погано: новий формат = зміна цього методу
string Export(Summary s, string format) => format switch
{
    "md"  => ToMarkdown(s),
    "csv" => ToCsv(s),
    _     => throw new NotSupportedException(format),
};
```

Якщо винести кожен формат в окремий клас, що реалізує спільний інтерфейс `IExporter`, новий формат додається новим класом, а наявний код не змінюється. Принцип відкритості/закритості тісно пов'язаний із поліморфізмом: саме поліморфізм дає змогу розширювати поведінку без редагування клієнта.

## 5.4. Принцип підстановки Лісков

Барбара Лісков сформулювала його так: якщо S є підтипом T, то об'єкти типу T у програмі можна замінити об'єктами типу S без порушення бажаних властивостей програми. Простіше кажучи, нащадок не повинен ламати очікування, які клієнт має щодо базового типу.

Класичний приклад порушення — квадрат, успадкований від прямокутника. З погляду геометрії квадрат є прямокутником, але в коді прямокутник має незалежні ширину й висоту:

[стор. 19]

```csharp
void Stretch(Rectangle r)
{
    r.Width = 10;
    r.Height = 5;
    Debug.Assert(r.Area() == 50);   // для Square не виконується
}
```

Клас `Square`, щоб залишатися квадратом, змінює висоту разом із шириною, і після виклику `Stretch` площа дорівнює 25, а не 50. Клієнт, написаний для прямокутника, ламається, отримавши квадрат. Інші ознаки порушення принципу: нащадок кидає `NotSupportedException` у методі бази, посилює передумови (вимагає більше, ніж база) або послаблює післяумови (гарантує менше, ніж база).

Розв'язання зазвичай полягає в тому, щоб переглянути ієрархію: зробити фігури незмінними (тоді проблеми зі зміною сторін немає) або не успадковувати `Square` від `Rectangle`, а мати спільний базовий тип `Shape`.

## 5.5. Принцип розділення інтерфейсів

Клієнти не повинні залежати від методів, якими вони не користуються. Замість одного великого інтерфейсу краще мати кілька вузьких, кожен під потреби певної групи клієнтів. Наприклад, вікну історії потрібні лише читання і пошук сесій, а сервісу запису — лише додавання сегментів. Якщо обидва залежать від одного інтерфейсу з двадцятьма методами, зміна будь-якого з них зачіпає обох.

Водночас дробити інтерфейси до одного методу без потреби теж не варто: метою є зручність клієнтів, а не мінімальний розмір інтерфейсу.

## 5.6. Принцип інверсії залежностей

Модулі верхнього рівня не повинні залежати від модулів нижнього рівня; обидва мають залежати від абстракцій. Абстракції не повинні залежати від деталей; деталі мають залежати від абстракцій.

Без інверсії залежностей бізнес-логіка безпосередньо створює й викликає інфраструктурні класи: `new SqliteConnection(...)`, `new HttpClient()`, `new OpenAIClient(key)`. Через це її неможливо протестувати без бази даних і мережі, а заміна провайдера вимагає переписати логіку.

З інверсією залежностей ядро оголошує інтерфейс, який йому потрібен (`ILlmClient`, `ILectureStore`), а інфраструктурний проєкт його реалізує. Напрямок залежності в коді стає протилежним напрямку виклику: ядро викликає інфраструктуру, але залежить лише від власного інтерфейсу. Конкретну реалізацію передають через конструктор — це називають впровадженням залежностей (dependency injection):

```csharp
public sealed class AnswerService
{
    private readonly ILlmClient _llm;

    public AnswerService(ILlmClient llm) => _llm = llm;
}
```

[стор. 21]

У тестах `AnswerService` отримує фейковий клієнт, у режимі «Демо» — детерміновану імітацію, а в робочому режимі — справжнього провайдера. Код самого сервісу при цьому не змінюється. Об'єкти зазвичай збирає контейнер впровадження залежностей (наприклад, `Microsoft.Extensions.DependencyInjection`) у точці входу програми.

## 5.7. SOLID і здоровий глузд

Принципи SOLID — це орієнтири, а не закони. Їх механічне застосування призводить до надмірної кількості дрібних класів та інтерфейсів, у яких важко орієнтуватися. Корисне правило YAGNI (You Aren't Gonna Need It) нагадує: не додавайте абстракцію, доки вона не потрібна для реальної задачі — другої реалізації, тестування або ізоляції від зовнішньої бібліотеки.

**Підсумок лекції.** SOLID допомагає будувати код, у якому зміни локальні й передбачувані. Єдина відповідальність зменшує причини для змін, відкритість/закритість спирається на поліморфізм, підстановка Лісков захищає клієнтів від несподіваних нащадків, вузькі інтерфейси зменшують зв'язність, а інверсія залежностей робить ядро незалежним від інфраструктури.
