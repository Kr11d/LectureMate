# Лекція 7. Винятки та обробка помилок

[стор. 27]

## 7.1. Помилки, які неминучі

Програма працює у ненадійному світі: файл може бути зашифрованим, мережа — недоступною, сервіс — перевантаженим, а користувач може натиснути «Стоп» у найнесподіваніший момент. Добре спроєктована програма не прикидається, що цього не буває, а явно описує, як поводитися в кожній ситуації. Розрізняють три категорії проблем:

- **помилки програміста** (null там, де його не може бути; вихід за межі масиву). Їх не обробляють, а виправляють; виняток тут — сигнал про дефект;
- **очікувані ситуації предметної області** (набір матеріалів перевищує бюджет токенів, користувач увів порожню назву курсу). Їх зручніше повертати як звичайний результат або стан об'єкта, а не як виняток;
- **збої зовнішнього середовища** (обрив з'єднання, відповідь 429 або 503, пошкоджений файл). Для них і призначені винятки та стратегії відновлення: повтор, резервний варіант, зрозуміле повідомлення.

## 7.2. Механізм винятків у C#

Виняток — це об'єкт класу, похідного від `System.Exception`, який кидають оператором `throw`. Виконання поточного методу припиняється, і середовище шукає найближчий блок `catch`, що підходить за типом. Блок `finally` виконується завжди — і при нормальному завершенні, і при винятку — тому в ньому звільняють ресурси. Ще зручніше використовувати `using`, який викликає `Dispose` автоматично.

[стор. 28]

```csharp
try
{
    var pages = await extractor.ExtractPagesAsync(stream, ct);
    return new PdfDocument(title, pages);
}
catch (InvalidPdfException ex)
{
    throw new ContextLoadException($"Не вдалося прочитати «{title}».", ex);
}
```

Тут низькорівневий виняток бібліотеки перетворюється на виняток рівня програми, а оригінал зберігається у властивості `InnerException`. Так верхні рівні не залежать від винятків сторонньої бібліотеки, але інформація для діагностики не губиться.

Фільтри винятків (`catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.TooManyRequests)`) дозволяють перехоплювати виняток лише за певної умови, не розгортаючи стек для решти випадків.

## 7.3. Власна ієрархія винятків

Для великої програми корисно мати власну ієрархію винятків з абстрактним базовим класом:

```csharp
public abstract class LectureMateException : Exception
{
    protected LectureMateException(string message, Exception? inner = null) : base(message, inner) { }
}

public sealed class LlmProviderException : LectureMateException
{
    public LlmProviderException(string message, int? statusCode, bool isRetryable, Exception? inner = null)
        : base(message, inner)
    {
        StatusCode = statusCode;
        IsRetryable = isRetryable;
    }

    public int? StatusCode { get; }
    public bool IsRetryable { get; }
}
```

[стор. 29]

Спільний базовий клас дозволяє верхньому рівню перехопити всі «наші» винятки одним `catch`, а нащадки несуть додаткову інформацію: код відповіді сервера, чи має сенс повторювати запит. Відповіді 429 (забагато запитів) і 5xx (помилка сервера) зазвичай тимчасові, тож запит повторюють із затримкою. Відповіді 400, 401 і 403 означають помилку в запиті або ключі, і повтор нічого не змінить.

## 7.4. Чого не можна робити з винятками

- **Порожній `catch`.** Конструкція `catch (Exception) { }` «ковтає» помилку: програма продовжує працювати в невідомому стані, а причину збою вже не знайти. Кожна перехоплена помилка має бути або оброблена (повтор, резервний варіант), або залогована й показана користувачу, або перекинута далі.
- **`throw ex;` замість `throw;`.** Перший варіант скидає стек викликів, і в лозі видно лише місце повторного кидання, а не справжнє джерело помилки.
- **Винятки для керування потоком виконання.** Кидати виняток, щоб вийти з циклу або повернути «звичайний» результат, повільно й заплутує код.
- **Перехоплення `Exception` скрізь.** Перехоплюйте лише ті типи, які ви вмієте обробити. Неочікувані винятки нехай доходять до глобального обробника, який залогує їх і покаже повідомлення.

## 7.5. Повтори, таймаути та скасування

Для збоїв мережі застосовують повтор з експоненційною затримкою (exponential backoff): після першої невдачі чекають 1 с, потім 2, 4, 8 і так далі до встановленої межі. Це не перевантажує сервіс і дає йому час відновитися. Важливо повторювати лише ідемпотентні операції або операції, які ще не почали віддавати результат: якщо відповідь моделі вже частково показана користувачу, повтор із початку створить дублікати.

[стор. 30]

Довгі операції в .NET приймають `CancellationToken`. Скасування — не помилка, а нормальна подія: користувач поставив нове питання, і стара відповідь більше не потрібна. Метод, отримавши скасування, кидає `OperationCanceledException`, і код, що його викликав, не повинен показувати це як збій.

Таймаут реалізують через той самий механізм: `CancellationTokenSource.CancelAfter(TimeSpan.FromSeconds(8))`. Якщо за вісім секунд модель не надіслала жодного токена, запит скасовується, а користувач бачить повідомлення і кнопку «Повторити».

## 7.6. Логування помилок

Кожна оброблена помилка має залишити слід у журналі: що сталося, у якому контексті (ідентифікатор сесії, етап обробки), скільки тривало. Структуроване логування записує ці дані як окремі поля, тож журнал можна фільтрувати й аналізувати. Водночас у журнал ніколи не пишуть секрети — ключі API, паролі, персональні дані. Великі тексти, як-от повний промпт, теж не логують: достатньо довжини та хешу, щоб порівнювати запити.

**Підсумок лекції.** Помилки програміста виправляють, очікувані ситуації повертають як результат, а збої середовища обробляють винятками. Власна ієрархія винятків відокремлює помилки програми від помилок бібліотек. Порожній `catch` приховує збої, тому кожен перехоплений виняток треба обробити, залогувати або перекинути далі.
