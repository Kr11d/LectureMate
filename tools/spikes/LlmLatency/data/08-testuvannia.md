# Лекція 8. Модульне тестування об'єктно-орієнтованого коду

[стор. 31]

## 8.1. Навіщо писати тести

Модульний (unit) тест перевіряє невелику частину програми — клас або метод — ізольовано від решти системи. Тести дають три переваги. По-перше, вони знаходять помилки одразу після внесення змін, а не через тиждень на демонстрації. По-друге, вони дозволяють сміливо змінювати код: якщо після рефакторингу всі тести зелені, поведінка не зламалася. По-третє, тести документують код: з тесту видно, як клас призначений використовуватися і що він гарантує.

Добрий модульний тест має властивості, які запам'ятовують за абревіатурою FIRST: швидкий (Fast), незалежний від інших тестів (Independent), відтворюваний у будь-якому середовищі (Repeatable), самоперевірний — сам повідомляє, пройшов чи ні (Self-validating), і написаний вчасно (Timely), разом із кодом.

## 8.2. Структура тесту

Найпоширеніша структура тесту — «Arrange, Act, Assert»: підготувати об'єкти, виконати дію, перевірити результат.

```csharp
public sealed class BankAccountTests
{
    [Fact]
    public void Withdraw_MoreThanBalance_Throws()
    {
        // Arrange
        var account = new BankAccount("Олена", initialBalance: 100);

        // Act
        var act = () => account.Withdraw(150);

        // Assert
        Assert.Throws<InvalidOperationException>(act);
        Assert.Equal(100, account.Balance);
    }
}
```

[стор. 32]

Назва тесту описує сценарій і очікуваний результат: що тестується, за яких умов і що має статися. Один тест перевіряє одну поведінку. Якщо тест падає, з його назви має бути зрозуміло, що саме зламалося.

Параметризовані тести (`[Theory]` з `[InlineData]` у xUnit) перевіряють ту саму поведінку на наборі вхідних даних. Це зручно для таблиць: коди відповідей сервера і чи можна їх повторювати, фрази і чи вважає їх детектор питанням.

```csharp
[Theory]
[InlineData(429, true)]
[InlineData(503, true)]
[InlineData(401, false)]
[InlineData(400, false)]
public void IsRetryable_DependsOnStatusCode(int status, bool expected)
{
    var ex = new LlmProviderException("test", status, isRetryable: expected);
    Assert.Equal(expected, ex.IsRetryable);
}
```

## 8.3. Тестові двійники

Клас рідко працює сам: він залежить від сховища, мережевого клієнта, годинника. Щоб тест був швидким і відтворюваним, реальні залежності замінюють тестовими двійниками (test doubles):

- **заглушка** (stub) повертає заздалегідь задані відповіді;
- **імітація** (mock) додатково дозволяє перевірити, які методи і з якими аргументами викликали;
- **фейк** (fake) — спрощена робоча реалізація, наприклад сховище в пам'яті або LLM-клієнт, що повертає детерміновану відповідь із невеликою затримкою.

[стор. 33]

Тестові двійники можливі лише тоді, коли клас залежить від абстракції, а не створює залежність сам. Ось чому інверсія залежностей і тестованість ідуть поруч: інтерфейс `ILlmClient` дозволяє перевірити логіку обробки відповіді, не відправляючи жодного запиту в мережу. Бібліотеки на зразок NSubstitute створюють двійники автоматично:

```csharp
var llm = Substitute.For<ILlmClient>();
llm.StreamAsync(Arg.Any<LlmRequest>(), Arg.Any<CancellationToken>())
   .Returns(Tokens("NO_", "QUESTION"));

var service = new AnswerService(llm);
await service.AskAsync(question, AnswerMode.Auto, screenshot: null, CancellationToken.None);

Assert.Equal(QaStatus.Discarded, service.LastStatus);
```

Час теж є залежністю. Код, який викликає `DateTime.Now` або `Task.Delay` напряму, важко тестувати: тест або чекатиме реальні секунди, або залежатиме від годинника. Абстракція `TimeProvider` із BCL дозволяє в тесті «перемотати» час миттєво.

## 8.4. Що тестувати насамперед

Найбільшу користь дають тести для логіки з розгалуженнями: евристик, розрахунків, станів і переходів, обробки помилок. Тестувати прості властивості й конструктори, що лише присвоюють значення, сенсу мало. Окремо варто перевіряти граничні випадки: порожній список, рівно граничне значення бюджету, скасування посеред операції, повтор після тимчасової помилки.

[стор. 34]

Тести, що звертаються до справжніх зовнішніх сервісів, корисні, але повільні, платні й нестабільні. Їх позначають окремою категорією і запускають вручну або за розкладом, а не при кожній збірці. Основний набір тестів має проходити без мережі й без ключів.

## 8.5. Мікробенчмарки

Модульні тести перевіряють правильність, а мікробенчмарки — швидкодію. Наївне вимірювання через `Stopwatch` у циклі дає ненадійні результати: заважають прогрів JIT-компілятора, збирання сміття, інші процеси. Бібліотека BenchmarkDotNet автоматично прогріває код, повторює виміри, рахує статистику (середнє, медіану, розкид) і показує, скільки пам'яті виділено. Бенчмарк має сенс для коду на «гарячому» шляху: наприклад, евристика детектора питань повинна працювати за мікросекунди, бо викликається на кожному сегменті транскрипту.

**Підсумок лекції.** Модульні тести знаходять регресії, полегшують рефакторинг і документують поведінку. Тест має структуру «Arrange, Act, Assert» і перевіряє одну поведінку. Залежності замінюють тестовими двійниками, що можливо завдяки інверсії залежностей. Тести зі справжніми сервісами відокремлюють від основного набору, а швидкодію вимірюють бенчмарками.
