## 4.1. Абстрактні класи

Абстрактний клас — це клас, екземпляр якого створити не можна. Він існує для того, щоб бути базою для нащадків. Абстрактний клас може містити як звичайні методи з реалізацією, так і абстрактні методи — оголошені без тіла. Кожен неабстрактний нащадок зобов'язаний реалізувати всі абстрактні методи.

```csharp
public abstract class ContextItem
{
    protected ContextItem(string title) => Title = title;

    public string Title { get; }
    public bool IsEnabled { get; set; } = true;

    public abstract int EstimateTokens();

    public override string ToString() => $"{Title} (~{EstimateTokens()} токенів)";
}

public sealed class TextNote : ContextItem
{
    public TextNote(string title, string text) : base(title) => Text = text;

    public string Text { get; }

    public override int EstimateTokens() => (Text.Length + 3) / 4;
}
```

Абстрактний клас доречний, коли нащадки мають спільний стан (тут — `Title` і `IsEnabled`) і спільну поведінку, а відрізняються лише деякими операціями. Він також може захищати інваріанти бази: конструктор `protected` перевіряє аргументи один раз для всіх нащадків.

## 4.2. Інтерфейси

Інтерфейс описує лише контракт: які операції має надати тип. Сучасні версії C# дозволяють інтерфейсам містити реалізації методів за замовчуванням і статичні члени, але головне призначення інтерфейсу залишилося тим самим — визначити, що вміє об'єкт, не кажучи, як він це робить.

Клас може реалізувати багато інтерфейсів, тоді як базовий клас у нього лише один. Тому інтерфейси добре описують окремі можливості: `IDisposable` (об'єкт треба звільнити), `IComparable<T>` (об'єкти можна порівнювати), `IAsyncEnumerable<T>` (послідовність можна обходити асинхронно).

## 4.3. Чим абстрактний клас відрізняється від інтерфейсу

| Ознака | Абстрактний клас | Інтерфейс |
|---|---|---|
| Скільки можна успадкувати | Один | Багато |
| Поля екземпляра (стан) | Так | Ні |
| Конструктор | Так | Ні |
| Модифікатори доступу членів | Будь-які | Здебільшого `public` |
| Відношення | «є різновидом» | «вміє робити» |
| Типове використання | Спільна реалізація родини класів | Межа між модулями, підміна в тестах |

Практичне правило: якщо потрібна межа між частинами системи, з якою працюватимуть клієнти, оголошуйте інтерфейс. Якщо кілька реалізацій цього інтерфейсу мають багато спільного коду, додайте абстрактний базовий клас, що реалізує інтерфейс. Так влаштовано багато бібліотек: `Stream` — абстрактний клас, а `IDisposable`, який він реалізує, — інтерфейс.

## 4.4. Інтерфейс як межа із зовнішнім світом

Особливо важливі інтерфейси на межі програми із зовнішнім світом: файловою системою, мережею, базою даних, звуковою картою, сторонніми сервісами. Якщо бізнес-логіка залежить від інтерфейсу `ILlmClient`, а не від конкретного SDK провайдера, то:

- логіку можна протестувати з фейковою реалізацією, без мережі й без ключів API;
- провайдера можна замінити, не змінюючи бізнес-логіку;
- основний проєкт не залежить від сторонньої бібліотеки, тож її оновлення не зачіпає ядро.

Водночас не варто створювати інтерфейс для кожного класу «про всяк випадок». Інтерфейс має сенс, коли існує друга реалізація, потреба підмінити залежність у тестах або потреба ізолювати ядро від бібліотеки чи операційної системи. Чистий детермінований клас, наприклад евристичний аналізатор тексту, можна тестувати напряму, і інтерфейс йому не потрібен.

## 4.5. Явна реалізація інтерфейсу

Іноді клас реалізує два інтерфейси з однаковими назвами методів або хоче приховати член інтерфейсу від звичайного використання. Тоді застосовують явну реалізацію:

```csharp
public sealed class Session : IAsyncDisposable
{
    async ValueTask IAsyncDisposable.DisposeAsync() => await StopAsync();
    public Task StopAsync() => Task.CompletedTask;
}
```

[стор. 16]

Метод, реалізований явно, доступний лише через посилання типу інтерфейсу: `((IAsyncDisposable)session).DisposeAsync()`. У звичайному коді його не видно, а `await using` знаходить його автоматично.

## 4.6. Типові помилки

- Інтерфейс з одним методом на кожен клас і без другої реалізації — зайвий рівень непрямості, який ускладнює навігацію кодом.
- «Товстий» інтерфейс із двадцятьма методами, з яких кожному клієнту потрібні два. Таке порушення принципу розділення інтерфейсів змушує реалізації писати порожні методи-заглушки.
- Абстрактний клас без абстрактних членів і без спільного стану. Зазвичай це ознака того, що замість нього потрібен інтерфейс або звичайний клас.
- Перевірки типу на зразок `if (item is PdfDocument pdf) ... else if (item is ImageItem img) ...` у клієнтському коді. Якщо поведінка залежить від типу, її краще перенести у віртуальний метод самого класу.

**Підсумок лекції.** Абстрактний клас поєднує спільний стан і спільну реалізацію родини класів, інтерфейс задає контракт без стану. Інтерфейси особливо цінні на межі із зовнішнім світом, але створювати їх варто лише тоді, коли є реальна потреба.
